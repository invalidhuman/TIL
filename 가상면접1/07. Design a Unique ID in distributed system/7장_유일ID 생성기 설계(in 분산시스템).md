
# Ch7. Design a Unique ID Generator in Distributed Systems

이 책을 읽어오면서 각 장이 개략적으로 어떤 차이가 있는 건지 흐름이 잘 잡히지 않아서 4,5,6,7장의 주제를 추상적으로 바꿔서 정리해보았다.

- 4장 (Rate Limiter) : 처리율 제한기(미들웨어 서버)가 여러 대인 상황
- 5장(Consistent Hash), 6장(Key-Value Store) : 데이터를 저장하는 서버(노드)가 여러 대인 상황
- **7장 : ID를 만드는 곳이 여러 곳인 상황**

### Unique ID (유일 ID)란?

DB에 저장되는 모든 기록에는 각각에 ID 가 붙어야한다.

- 사용자 : user_id
- 게시글 : post_id
- 주문 : order_id
- 댓글 : comment_id

#### '분산 환경'에서의 Unique ID 설계를 고민해야하는 이유

분산환경이 아닌 경우 DB가 한 대이므로,  
auto_increment 속성으로 해도 중복 문제가 없다.

<aside>  
💡

auto_increment

MY SQL에서 테이블을 만들 때, ID 컬럼에 사용하는 속성

새 행을 추가할 때 DB가 자동으로 번호를 자동으로 배정

```sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(200)

```

DB가 여러 대이면, auto increment 속성을 쓸 경우

1. 각자 1부터 세느라  
    서로 다른 게시글인데 post_id가 겹치는 문제가 발생할 수 있다.
2. 여러 데이터베이스 서버 쓰는 경우 auto increment로 했을 때 지연 시간을 낮추기가 힘들어진다.

그렇다고 데이터베이스 한 대를 쓰는 건 분산환경에서의 요구를 감당할 수 없으니,

**여러 대가 동시에 번호를 붙여도 중복되지 않게 하는 설계**를 할 줄 알아야한다.


### 유일성이 보장되는 ID의 예 4가지

- 다중마스터 복제 (multi-master replication)
- UUID
- 티켓 서버 Ticket Sever
- Twitter Snowflake


다중 마스터 복제(Multi-Master replication)

데이터베이스의 auto_increment 기능 활용하되,  
다음 ID의 값을 구할 때 1만큼 증가시키는 개 아니라 DB 서버 수만큼 증가시킨다.

DB 서버 수를 k라 하면,

k = 2 이면 DB 한 대는 1, 3, 5… 다른 한 대는 2, 4, 6 을 발급한다.

단점

- 여러 데이터센터에 걸쳐 규모를 늘리기 어렵다.
    
- 서버 전체에서 ID가 시간순으로 증가하도록 보장할 수 없다.
    
    【이해용 예시】 서버 A가 먼저 101을 만들고, 나중에 서버 B가 20을 만들 수도 있다. 중복은 없지만 생성 시각과 ID의 크기 순서가 다르다.
    
- 서버를 추가하거나 삭제할 때 증가 폭과 시작 번호를 다시 조정하기 어렵다.


Universally unique identifier (UUID)

컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트 짜리 수

**장점**

- 충돌 가능성이 지극히 낮다.
    
    > 중복 UUID가 1개 생길 확률을 50%로 끌어올리려면 초당 10억 개의 UUID를 약 100년 동안 계속해서 만들어야 한다.
    
- 만드는 것이 단순하다.
    
- UUID는 서버 간 조율 없이 독립적으로 생성 가능하다. ⇒ **동기화 이슈가 없다.**
    
- 각 서버가 자기가 쓸 ID를 알아서 만드는 구조이므로 ⇒ **규모 확장이 쉽다.**
    

**단점**

- ID가 128비트로 길다.
- 책에서 다루는 UUID 방식은 시간순 정렬 요구사항을 만족하지 못한다.
- 일반적인 문자열 표기에 영문자와 하이픈이 포함된다. UUID 자체는 128비트 값이며, 이번 문제에서는 64비트 길이 제한이 핵심 제약이다.


티켓 서버
auto_increment 기능을 갖춘 데이터베이스 서버를 중앙 집중형으로 하나만 사용하는 방식
**장점**

- 오직 숫자로만 구성된 유일 ID를 쉽게 만들 수 있다.
- 구현이 쉽다. 중소 규모 애플리케이션에 적합

**단점**

- 티켓 서버가 SPOF(단일장애점)가 된다.
    
    티켓 서버에 장애가 발생하면 해당 서버를 이용하는 모든 시스템이 영향을 받는다.
    
    티켓 서버를 여러 대 준비하는 식으로 대비할 수 있으나 동기화문제같은 새로운 문제가 발생한다.
    

사용 사례

- **Flickr : 분산 기본 키(distributed primary key)**를 만들어내기 위해 **티켓 서버** 사용

### Twitter Snowflake 접근법

- ID는 유일해야 한다.
- ID는 숫자로만 구성되어야 한다.
- ID는 64비트로 표현될 수 있는 값이어야 한다.
- ID는 발급 날짜에 따라 정렬 가능해야 한다.
- 초당 10,000개의 ID를 만들 수 있어야한다.

를 모두 만족한다.

64비트 ID의 구조


- sign 비트 : **1비트**. 이 설계에서는 0으로 두고, 향후 사용을 위해 유보한다.
    
- 타임스탬프 : **41비트**. epoch(기원 시각) 이후로 몇 ms가 경과했는지 나타낸다.
    
- 데이터센터 ID : **5비트**. 2의 5제곱 = **32개 데이터센터**를 구분할 수 있다.
    
- 서버 ID : **5비트**. 데이터센터마다 **32대 서버**를 구분할 수 있다.
    
- sequence number (일련번호) : **12비트**. 같은 서버가 같은 ms에 만든 ID를 구분한다.
    
    각 서버에서는 ID를 생성할 때마다 일련번호를 1만큼 증가시킨다.
    
    새로운 ms가 되면 0부터 다시 시작한다.
    

**합계 : 1 + 41 + 5 + 5 + 12 = 64비트**

데이터센터 ID와 서버 ID는 시스템 시작 시 결정하며, 운영 중에는 일반적으로 바꾸지 않는다. 잘못 변경하거나 중복 배정하면 ID 충돌이 생길 수 있다.

타임스탬프와 일련번호는 ID를 생성하는 동안 계속 달라진다.

## 타임스탬프

**Snowflake**에서 다룬 ID 구조에서 가장 중요한 41비트를 차지하고 있다.

**타임스탬프**는 시간이 흐름에 따라 점점 큰 값을 갖게 되므로, 결국 ID는 시간 순으로 정렬 가능하게 된다.

41비트로 표현할 수 있는 타임스탬프의 최댓값은 **2의 41제곱 - 1 = 2,199,023,255,551ms**로, 약 **69.7년**이다. 책에서는 대략 69년으로 설명한다.

### epoch (기원 시각)이란?

시간을 세기 시작하는 기준점이다. 타임스탬프에는 날짜 문자열 대신 **현재 시각 - 기원 시각**을 ms 단위로 저장한다.

책의 설계에서 사용하는 기원 시각은 **1288834974657ms**, 즉 **2010년 11월 4일 01:42:54 UTC**이다.

책 그림 7-7의 변환 과정을 숫자로 보면 다음과 같다.

```
ID의 타임스탬프 부분 → 297616116568ms
기원 시각을 더함     → 297616116568 + 1288834974657
                    = 1586451091225ms
UTC 시각으로 변환    → 2020-04-09 16:51:31.225 UTC
```

기원 시각을 서비스 시작 시점에 가깝게 정하면, 타임스탬프 범위를 더 오래 사용할 수 있다. 약 69년이 지나면 범위를 다 쓰므로 ID 체계 이전 계획이 필요하다.

【이해를 위한 보충】 운영 중 기원 시각만 임의로 바꾸면 기존 ID와 충돌할 수 있으므로, 기존 ID와 구분되는 이전 방안을 함께 설계해야 한다.

## 일련번호

12비트이므로 **0부터 4095까지, 총 4096개 값**을 가질 수 있다. 따라서 서버 한 대에서 1ms에 최대 4096개의 서로 다른 ID를 표현할 수 있다.

같은 서버·같은 ms에서는 일련번호가 달라지고, 다음 ms에는 타임스탬프가 달라지므로 일련번호를 다시 0부터 쓸 수 있다.

【이해용 예시】 아래는 실제 ID 문자열이 아니라, ID 내부의 각 부분을 나누어 적은 것이다.

```
시각(ms) | 센터 | 서버 | 일련번호
1000     | 1    | 3    | 0
1000     | 1    | 3    | 1  ← 같은 서버, 같은 시각: 순번이 다름
1000     | 1    | 4    | 0  ← 같은 시각: 서버가 다름
1001     | 1    | 3    | 0  ← 다음 ms: 시각이 다름
```

【구현 시 보충】 같은 ms에서 4096개를 모두 썼다면 번호를 다시 쓰면 안 된다. 다음 ms까지 기다리는 등의 처리가 필요하다.

### 시간순 정렬의 의미

타임스탬프가 서버 ID와 일련번호보다 높은 자릿수에 있으므로, 정상적인 시계를 전제로 더 큰 타임스탬프의 ID가 더 크다.

【정확히 이해하기】 같은 ms에 서로 다른 서버에서 만든 ID의 실제 생성 순서까지 보장하는 것은 아니다. 서버 시계가 어긋나는 문제도 따로 다뤄야 한다.

### 마무리 : 왜 Snowflake를 선택했는가?

다중 마스터 복제, UUID, 티켓 서버를 비교한 뒤, 이번 문제의 요구사항을 만족하고 분산 환경에서 규모 확장이 가능한 **Snowflake 방식**을 선택했다.

- 다중 마스터 복제 : ID 중복은 피할 수 있지만 시간순 증가와 서버 증감 처리가 어렵다.
- UUID : 서버 간 조율 없이 만들 수 있지만 128비트여서 이번 문제의 64비트 조건에 맞지 않는다.
- 티켓 서버 : 구현은 쉽지만 중앙 발급 서버가 단일 장애점이 된다.
- Snowflake : **시간 + 데이터센터 + 서버 + 일련번호**를 합쳐 서버마다 독립적으로 ID를 만든다.
