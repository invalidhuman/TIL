앱에서는 웹의 composite 단계가 곧 레이어 합성 후 화면에 표시하는 단계이다.

ios : 메인 스레드가 UI KIT 으로, 레이어 트리만 갱신하고 커밋한다.  
실제 합성은 Render Server 라는 별도 시스템 프로세스가 GPU가 한다.

android : 메인 스레드는 display list 만 기록한다. GPU에 명령을 보내는 건 Render Thread가 하고, 최종 화면 합성은 SurfaceFlinger (시스템 프로세스)가 한다.

웹에서는 CSS 의 transform / opacity 애니메이션을 compositor 스레드가 직접 돌리므로 메인스레드가 막혀도 애니메이션이 부드럽다.

RN의 Reanimated는 매 프레임 UI 스레드(메인 스레드)에서 값을 계산해서 뷰 속성을 바꾼다.  
합성기가 알아서 돌리는 구조가 아니다.

iOS와 Android 모두 화면에 실제로 그리는 일과 터치 입력을 받는 일은 메인 스레드 하나에서만 하도록 정해져있다.

### **프레임 / 프레임 예산**

화면은 1초에 60번 혹은 120번 새로 그려지며,  
그러므로 한 장을 준비할 시간이 정해져있다.

- 60hz : 한 장에 약 16.7ms
- 120hz : 8.3ms (iPhone Pro 계열과 Android 기기)

이 시간 안에 다음 장면 한 장을 못만들면 그 프레임을 건너뛰게 되며,  
이를 **프레임 드랍**이라 한다.

⇒ 사용자는 버벅임으로 느낀다.

### 동기(sync)와 비동기(async)

비동기는 막히지 않는다는 장점이 있지만,

### React의 렌더링

- React 컴포넌트 함수가 다시 실행디는 것을 리렌더라고 한다.
- state나 props가 바뀌면 리렌더가 일어난다.
- React는 리 렌더 결과를 이전 결과와 비교(diffing)해서 실제로 바뀐 부분만 화면에 반영한다.
- 리렌더 자체는 JavaScript 연산이라 비용이 발생하며,  
    너무 자주, 크게 일어나면 JS 스레드가 바빠진다.

### 프레임마다 JS 스레드를 기다리는 구간을 없애야 한다.

---

UI Thread와 JS Thread 간의 메시지를 주고 받는다.

스레드마다 작업 큐가 있는데, 다른 스레드에 일을 시킨다는 건,  
그 스레드의 큐에 작업을 넣고 차례가 올 때까지 기다려야한다는 뜻이다.

손가락으로 카드를 끄는 동작을 JS Thread가 처리한다고 하면, 손가락이 조금움직일때마다 다음의 일이 일어난다.

```jsx
① [UI 스레드]  터치 이동 감지 (x=120)
② [UI → JS]   "손가락이 x=120으로 움직였어" 작업을 JS 큐에 넣음
③ [JS 스레드]  ⏳ 큐에서 차례 기다림  ← JS가 다른 일(8ms짜리 계산 등) 하는 중이면 여기서 대기
④ [JS 스레드]  핸들러 실행: translateX = 120 계산
⑤ [JS → UI]   "카드를 x=120으로 옮겨" 작업을 UI 큐에 넣음
⑥ [UI 스레드]  카드 위치 반영 → 화면에 그림
```

이 왕복이 프레임 예산 (60hz라면 약 16ms) 안에 끝나야 카드가 손가락에 붙어서 따라온다.

3번에서 js스레드가 바쁘면 결과가 다음 프레임이나 그 다음 프레임이 반영되므로 손가락보다 늦게 따라오거나 끊긴다.

그래서 프레임마다 JS 스레드를 기다려야한다는 의미가 된다.

### Worklet = UI Runtime에서도 실행할 수 있게 변환된 JS 함수

---

**JS 런타임**

- JS 코드를 실행하는 엔진 인스턴스. RN에서는 Hermes
- 원래 RN 앱에는 JS 스레드에 런타임이 하나 있고, 우리가 작성한 모든 JS 코드가 hermes에서 돈다.
- Reanimated는 UI Thread에 작은 런타임을 하나 더 띄운다. 이걸 UI Runtime 이라 한다.

```jsx
function calcRotation(dx:number) {

}

```

- 빌드할 때 Babel 플러그인이 이 함수의 코드와, 함수가 참조하는 바깥 변수의 값을 묶는다.
- 그리고 UI Runtime으로 복사할 수 있는 형태로 만든다.
